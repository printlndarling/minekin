## 3. 逐格设计

### 3.1 `ADMIT-090`（三格）

**格①「新 generation」——有判据，但它判的不是 generation 单独一项。**
`:2143` 那条比的是 `(session_id, generation)` 这一**对**，且拒止文本只把 `session[0]` 打出来。于是「session 换了、generation 仍从 1 数起」的重启是**过**的。反例 a：造一份 trace，让新 run 的每一行 `generation` 与上一 run 相同而 `session_id` 不同 ⇒ 判据不响，而契约的「新 generation」并没有被证。对策不是改这条断言：改函数体会移 `CORE-090` 里 `the_restart_runs_as_a_new_session` 的摘要（现值 `1b248b13…`，`core-090.json:14`），按 §1 的口径那等于给一份已封 bundle 换了判法。要单独判「新 generation」应当**新写一条具名断言**（不移旧案），并把它的口径写成「上一条 run 的最大 generation 与本次的最小 generation 之比」而不是「不等」——否则一次重启里两次尝试就能自证更新。

**格②「世界状态重验」——强读法场景不可达。**
`first_snapshot_admitted` 可复用，`domain.sh:1038-1042` 却又写明每 run 一份新目录且工具拒绝非空目录。所以契约 `:208` 那两连跑证的是「**同 Kin、新 run、新服务端目录**」，不是「重连同一份存档世界」，更不是「重连同一个服务端进程」。具名缺口：`SAME_WORLD_RECONNECT_NOT_REACHABLE_IN_P0`。要填它得让 harness 能把上一 run 的世界目录交回给新 run——那是 `test-orchestrator/**` 的改动加一次重封成本，属主控排期，本卡不预约。弱读法（同 Kin 新 run）今天**已经可达且已封过**，这是它与 `ADMIT-010` LAN 格的实质差别。

**格③「人格不重建」——从「无载体」改正为「有载体、无跨 run 判据」。**
旧清单（`docs/p0-evidence-inventory-2026-09-26.md:165`）按历史读数写的是「账本现有事件类型里没有一个承载身份/人格」。**这条在今天不成立**：`SessionIdentityCompared` 是产品自己写的 CORE 行（底数 #5），它的观测字段带名字与 UUID（#6），而上一条 run 的这行随 `previous-run-trace.jsonl` 一起封在 bundle 里（#7）。⇒ 「两次运行报出同一个身份」是**不需要产品新增事实**就能判的形状：新断言逐字段比两份 trace 的 identity payload，并先拒绝「本次没有 identity 行」（反例 b：本次不写 identity 行、上一条写了 ⇒ 只比「存在的那些」会恒真）。判不出的那半也说清楚：`local_profile_id`、`identity_revision`、`uuid_algorithm` 不在 payload 里（#8），所以「本地身份记录被重建但仍推导出同一个 name-derived UUID」这类形状今天看不见——那一半要动的是产品载荷，不是判据。

### 3.2 `ADMIT-120`（一格两半）

**仓库/构建侧不是「没有任何断言」，而是已有四道。** 底数 #11-14 是四道独立的门：摘要钉住 canary 文件、`runtime-input` 的 marker 扫描（且扫的是 6 份非空文件，不是空目录）、wheel 的**值级**扫描（路径名与内容都扫，这条最硬——它抓的是「值漏进产品」而不是「名字漏进产品」）、case manifest 的 `oracle_inputs` 边界。把 ADMIT-120 一句话写成「无断言」会低估这半。但**这四道全不在运行材料上**：`runtime_input_does_not_reference_oracle` 的实现是 pytest（`tools/check_case_assertions.py:177` → `test_fixture_boundaries.py:90`），而 registry 里根本没有 `W00-CONTRACT-001` 的 evidence 行（§1 底数）⇒ 这半连「被封过一次」都不是。

**运行期那半缺两样东西，缺的第一样不是判据而是生产者。** 契约 `:143` 要归档「服务端 oracle 时间线」，而 `domain.sh` 里 `canary` 0 命中（#15）：没有任何机制把 oracle 事实放进世界，也就没有任何运行材料可扫。具名缺口：`ORACLE_CANARY_HAS_NO_PLACEMENT_MECHANISM`。第二样才是判据：一旦有放置，扫描域必须**排除 oracle 自己的载体**——验收器侧那份时间线按定义就含着 canary 值，把它一起扫会得到必然的红。可判形状照 #16 那三条经验来写：(i) 数「出现在 Runtime 侧载体」的次数而不是数「提到」；(ii) 只判被 seal 的载体（`client_log`、run document、ledger payload、`server_log` 的观察侧），读不到的面（模型 prompt / Memory 这类本仓库不存在的面）单列具名拒止，不许并入 `0`；(iii) 阳性对照要能把一个真值放进其中一个载体并看到它变红。
另外一个必须先定的口径：本仓库的 Runtime 里没有 LLM，「prompt / Memory」在运行材料侧**没有对应物**，所以「不得进入 Runtime、Memory、prompt 或行动路径」 today 能落的只有「不得进入快照/感知载荷与按键路径」。要不要把这半写死为契约解释，是主控的决定（§4 第 4 条）。

## 4. 交主控的四条决定

1. `ADMIT-090` 的「同一服」取强读法（同存档世界 / 同服务端进程，需 `test-orchestrator/**` 改动 + 重封成本）还是弱读法（同 Kin 的新 run，已封过）。本卡两半都量清了，不替它选。
2. 「新 generation」是否值得单独判。若判，新写一条断言（不移 `CORE-090`）；若不判，契约 `:138` 那一格应改成「新 session 坐标」以免读成两条承诺。
3. 人格等式只用现有 7 个观测字段是否够。够 ⇒ 一条新断言、零产品改动、老 bundle 复判即可覆盖；不够 ⇒ 要往 `SessionIdentityCompared` 载荷加 `local_profile_id`/`identity_revision`，那是产品新增事实，且**已封 bundle 里没有这两个字段**——加判据而不重封，等于宣布旧 run 从未被这条判据看过。
4. `ADMIT-120` 是否真要放置 canary。要 ⇒ 需要服务端写入机制 + 验收器对照通道 + 「oracle 自己的载体排除在扫描域外」的口径；不要 ⇒ 把运行期那半明确改由构建期 containment 认领，并删掉 `:143` 里「服务端 oracle 时间线」的归档要求。
