## 1. 复现入口（本轮真实用过的命令）

LAN 形状的宿主**是一个客户端**（它把自己的世界 publish 到局域网），所以这一轮**没有 dedicated server jar 参与**，
命令里也就没有 `MINEKIN_SERVER_JAR`。三次真跑只有两处不同：第一/二次用 `420` 秒界，第三次用 `300` 秒界，
且第一次之前 joiner Kin 的 `run/session/` 目录还不存在（§5 的缺陷 A）。

```bash

export MSYS_NO_PATHCONV=1
# 三次真跑共用的形状：kin-01 是宿主、kin-04 是加入者、判据挂在加入者身上
MINEKIN_KIN_ID=kin-01 MINEKIN_DOMAIN_CASE=CORE-030 \
MINEKIN_DOMAIN_CASE_ON=joiner MINEKIN_DOMAIN_JOIN=kin-04 \
MINEKIN_DOMAIN_OPEN_LAN=1 MINEKIN_DOMAIN_LAN_PORT=25570 \
MINEKIN_DOMAIN_SECONDS=420 \
  bash test-orchestrator/runner/run.sh domain session start \
    --profile tests/fixtures/runtime-input/bundle-p0-core-1.21.4.json \
    --world-save tests/fixtures/saves/kinworld --world-name kinworld
#   → 第一次 .tmp/e-b4-core030-run.log（rc=2）
#   → 第二次 .tmp/e-b4-core030-run2.log（rc=1，FAIL 封证）
#   → 第三次 .tmp/e-b4-core030-run3.log（PASS 封证，仅 MINEKIN_DOMAIN_SECONDS=300）
```

`--world-save / --world-name` 是这一条 case 的**必要前提**：不传时 `domain.sh` 印
`domain: no server profile; this run joins no world`（三份日志的第 1 行都是它），世界仍会 publish，
但宿主 run document 里就没有 `world_snapshot`，判据第二半只能拒（`THE_HOST_RUN_RECORDED_NO_WORLD_OF_ITS_OWN`）。
加入者那侧不需要 profile 文件：`domain.sh` 在 joiner 分支现写一份 loopback 的
`/tmp/domain-join-profile.json`（`host 127.0.0.1`、`port ${lan_port}`、`auth_mode offline`），
并在 `MINEKIN_DOMAIN_CASE_ON=joiner` 时把 `--world-run-document /tmp/domain-session.json`（宿主的 run document）
交给封存步骤 —— 判据第二半正是拿这份**另一个 run 的字节**去比 case 的 pin。

第一次之前还做了一次操作准备（不是补丁，也没进任何提交）：

## 5. 两处必须公开的偏差（都不由本卡修）

**缺陷 A —— 加入者 Kin 全新时 `domain.sh` 静默 `rc=2`（确定性）。**
`test-orchestrator/runner/domain.sh:657` 在 `set -euo pipefail` 下做
`before=$(ls "/data/kin/${joiner}/run/session/" 2>/dev/null | sort)`：一个刚被 `session init` 出来、
从未起过会话的 joiner Kin 没有 `run/session/` 目录，`ls` 的退出码 2 直接终止整个 run，
而 stdout/stderr 都被 `2>/dev/null` 吞掉 —— 第一次真跑因此只留下三行日志（`.tmp/e-b4-core030-run.log`）
和一个 `rc=2`，没有任何一行说清是目录不存在。绕法是操作员先建那个空目录（§1 的 `mkdir -p`）。
**本卡没有改那行代码**（runner 不在 B2 的 `allowed_paths` 里，与已披露的 `import sys` 缺陷同一处置），
只把它作为缺陷报告交主控；这是「第二次起就能跑」的前提，所以写在这里而不是只写在交接里。

**偏差 B —— 第二次的 crash 到今天无法重现，不编根因。**
加入者客户端崩在 `RenderSystem.initBackendSystem` → `GLX._initGlfw`，
`IllegalStateException: Failed to initialize GLFW, errors: GLFW error during init: [0x1000E]Failed to detect any supported platform`
（crash report 前 6 行见 §2 那份 bundle；Core 自己的 stderr 为空、`ipc/` 为空，Bridge 按 fail-closed 记 `BRIDGE_FAULT`）。
量到了能量的边界：

- **不是渲染器/GPU 的问题**：崩溃那次与成功那次的 `environment.renderer_display` 逐字相同，
  都是 `llvmpipe (LLVM 20.1.2, 256 bits)`（日志 `.tmp/e-b4-core030-readout.log` §4）；第三刀那五条
  当前构建 bundle 也全是 `llvmpipe`（`.tmp/e-b4-x-display-probe.log`）。
- **joiner 的显示确实是被允许访问的那一个**：加入者走 `domain.sh:666` 的 `xvfb-run -a`，
  那个 server 以 `-auth /tmp/xvfb-run.XXX/Xauthority -nolisten tcp` 起；一个正在拨号的被管客户端
  的 `/proc/<pid>/environ` 实测是 `DISPLAY=:99` + `XAUTHORITY=/tmp/xvfb-run.lS3qfZ/Xauthority`
  （`.tmp/e-b4-client-env-probe.log`），同一窗口的对照行里 Core 自己是 `:100` 加它那一轮的
  `xvfb-run.Froxe9/Xauthority` —— 即 `XAUTHORITY` 与 `DISPLAY` 一起经
  `src/minekin_core/config.py:51-55` 的 `FORWARDED_VARIABLES` 转发了下去。那一窗口的 run
  走到 join 阶段、`crash-reports` 数为 **0**。
- **会话叠加不挡 X**：A–G 矩阵（`.tmp/e-b4-x-matrix.log` + `.tmp/e-b4-x-refusal-text.log`）：
  带 cookie → `llvmpipe`；**抽掉 `XAUTHORITY` → `Authorization required, but no authorization protocol specified`**；
  `TMPDIR`/`HOME` 重定向进会话叠加 → 仍 `llvmpipe`；harness 自持的 `:77`（无 `-auth`）在重定向前后都通；
  `DISPLAY=127.0.0.1:99` → `Error: unable to open display 127.0.0.1:99`（就是 `-nolisten tcp`）；
  `unix:99` → `llvmpipe`。**四条能拒止的路径都各自有名字，而崩溃那次的配置属于「全部允许」那一格。**
- **第三次一字未改地重跑就 PASS**（同命令、同卷、同构建）。

⇒ 结论只到「非确定性、当前构建上不可重现」为止。根因不写；材料（FAIL bundle + crash report + 两份日志）
留在卷上，等主控决定要不要为它开一张 X/GLFW 的诊断卡。
