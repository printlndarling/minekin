## 3. 逐格 oracle / 载体 / 反例 / 阳性对照

### 3.1 ADMIT-030 前半句「分类不同」

「分类不同」本质上是**跨场景的比较判据**：一份 bundle 只会携带一种失败，因此它要么被写成「本 run 的分类 ∈ 该场景允许的那个具名值，且 ∉ 另两个场景的值」（每格自足），要么被写成跨 bundle 比较（不可判）。本卡取前者，并在 §4 里把「一个 id 装三个互斥场景」的拆分决定交回主控——不拆而用 any-satisfying promotion，正向绿会顺带关掉互斥的负向判据。

**① 拒绝连接 ⇒ `…CONNECTION_REFUSED`（唯一今天形状可达的一格）**

- oracle：账本 `SessionInterrupted{phase:"FAILED", reason:"ADMISSION_FAILURE_REASON_CONNECTION_REFUSED"}` 至少一条，且**同一 run 的** `reason` 不出现 `…ADDRESS_INVALID` / `…ADDRESS_POLICY_BLOCKED` / `…DNS_FAILED` 冒充它（对照集合就是载体 #6 那条既有钉）。
- 载体：#1 #2 #3 #4 #5 #6 #9 全在；Java/Python 两条单测已在（载体 #6）。
- 今天是否闭合：**未闭合**——卷上没有任何 `ADMIT-030` bundle（本轮未挂卷，读数取 `docs/p0-evidence-inventory-2026-09-26.md` 的 case 普查与 fixture 缺席）。缺的是运行材料，不是断言词汇。
- 反例（设计，须红）：把某条 `SessionInterrupted` 的 `reason` 伪造成 `…ADDRESS_INVALID`（即退回 `:121` 更正前的错分类形状）⇒ 判红，且**不得**回落到「没读到就跳过」。判别式：真字节（`…CONNECTION_REFUSED`）不红。
- 阳性对照（不得红）：一份 dial 到 loopback 上没人听的端口、只留一条 `FAILED/…CONNECTION_REFUSED` 的运行。`tests/unit/test_bridge_admission.py:141-148` 的 docstring 明写这一类是「本仓库今天能在本地端到端产出的唯一失败类」。**本卡未跑**（不改卷）。

**② 超时 ⇒ `…CONNECT_TIMEOUT`（词有、形状可达，但读到的值有风险）**

- oracle：`SessionInterrupted{FAILED, …CONNECT_TIMEOUT}`；且**不得**把它与 Core 自己的有界取消混为一谈（见反例 b）。
- 载体：词与分类在（#1 `:29`、#2 `:36-37`）；形状可达——v2 的 host 允许任意规范化 IP 字面量（#10），故一个「可路由但静默」的地址不需要改任何 schema 就能进 profile。
- 风险（推断，且是本轮唯一无法在仓库字节里定论的一条）：netty 的 connect 默认不带超时，`SocketTimeoutException` 可能晚于 Core 的 30 秒具名超时（#8）到达 ⇒ 账本里更可能读到 `phase:FAILED` 搭配 `…CANCELLED`，或 run 文档出现 `connection_cancelled:"TIMEOUT"` 而**没有** `…CONNECT_TIMEOUT`。二者说的是不同的事。
- 反例 a（须红）：run 只有 `connection_cancelled:"TIMEOUT"` 而无任何 `…CONNECT_TIMEOUT` 账本行 ⇒ 该格判红为**具名缺口** `CONNECT_TIMEOUT_CLASSIFICATION_NOT_OBSERVED`，不得判「超时已被分类」。
- 反例 b（须红）：把 Core 自己发起的取消（`CancelConnection(TIMEOUT)`）当成 netty 的 `SocketTimeoutException` ⇒ 分类应落在 `…CANCELLED`，若伪造成 `…CONNECT_TIMEOUT` 该判红（对照载体 #8 与既有搭配表 `tests/unit/test_bridge_admission.py:206-216`，那里已钉住 `phase × reason × terminal` 的搭配）。
- 阳性对照（不得红）：一份真读到 `FAILED/…CONNECT_TIMEOUT` 的运行。**本卡未测**；并且它要求先决定「允许 dial 哪个静默地址」——属主控（§4 决定三），本卡不选地址、不 dial。

**③ 无 DNS ⇒ `…DNS_FAILED`（今天「场景不可达」，属可达性缺口）**

- 词汇与分类都在：枚举 `:27`、分类 `ConnectFailure.java:33-34`、mixin 的 ordinal 0 路径 `ConnectFailureMixin.java:44-56`，Java 单测 `ConnectFailureTest.java:29-31` 也钉住了它。
- **但运行材料无法经「已保存 profile」这条路产生**：v2 的 host 必须是 IP 字面量，代码里的具名拒止逐字写着「server profile host must be an explicit IP literal, not a resolvable name」（`server_profile.py:287-289`），v1 更是只允许两枚 loopback 字面量（`schemas/server-profile.schema.json:11`）。IP 字面量不走解析器 ⇒ `UnknownHostException` 在这一路径上没有成因。schema 的 pattern `^[0-9a-fA-F:.]+$` 看似能漏进一个「全是十六进制字母的假名字」（如 `ab.cd`），但它在 `_literal_host:286` 的 `ipaddress.ip_address()` 处就先被拒掉——**该漏洞不成立**（本轮按字面读码判定，未跑）。
- 结论：本格不是「缺断言」，也不是「缺分类词」，而是**场景不可达**。建议具名缺口 `DNS_SCENARIO_NOT_REACHABLE_BY_PROFILE`（先例：`tools/assert_case_evidence.py:4056` 的 `a_renamed_or_recased_login_is_not_called_a_duplicate` 直接返回 `CONFLICT_CATEGORY_HAS_NO_RENAME_ENTRY`，即在词汇/材料不足处报出所缺之物，而不是让空读作通过）。
- 反例（须红）：一份把 `reason` 写成 `…DNS_FAILED` 而 `client_log` 里没有任何解析失败痕迹、profile 又带着 IP 字面量的材料 ⇒ 判红（这条判的是「分类与更上游的证据互相矛盾」，因此它**必须**同时读 ledger 与 client 流；只读 ledger 的判据会被这类材料骗过）。
- 出路两条，均交主控（§4 决定三）：(甲) 让 profile 能携带一个保留的不可解析名（RFC 6761 的 `.invalid`）——那是 schema + `_literal_host` 的产品改动；(乙) 用今天已在范围内的形状替代（`CONNECTION_REFUSED` 与 `CONNECT_TIMEOUT` 两格），把 030 的「三分类」读法诚实收窄为「两分类 + 一条不可达登记」。本卡不选。

**④ case id 拆分（契约层，不是代码层）**

`:132` 一行把三个互斥场景塞进一个 id；`docs/p0-evidence-inventory-2026-09-26.md:290` 记的后果是「promotion 对同一 id 取任一满足 bundle，正向证据会顺带关掉互斥的负向判据」。三种可选形状（本卡不选，交主控）：拆成 `ADMIT-030A/B/C` 三个 id；保留单 id 但把「三格各自登记各自断言」写进 fixture（一个 bundle 只能满足自己那格）；或只登记可诚实判的那格、其余以缺口名报出。第三种与 §3.1③ 的写法一致，代价最小，但它把契约文本改了读法——所以仍是契约决定。

### 3.2 ADMIT-030 后半句「无无限重试」

这一句的可判形状不是「证明不存在循环」，而是「**本 run 的尝试次数有具名上限，并且它确实终止了**」。

- oracle（两条，必须同时成立）：
  1. 计数有界：`client_log` 里 `_DIALLED`（`tools/assert_case_evidence.py:1379`）匹配数 ≤ 一个**具名上限**，且 distinct generation ≤ 同一上限；上限值须由契约/fixture 命名，不能由判官取常量默认。
  2. 有终态：账本存在一条 `SessionInterrupted{FAILED, reason ∈ 该场景具名值}`，或 run 文档 `connection_cancelled` 非空（#8）——二者至少一条，且 `…UNSPECIFIED`/空 reason 不算。
- 载体：#9（dial 行 + generation 计数，已在既有判官里被使用）、#8（有界超时与具名 token）、#7（Bridge 无重试码 ⇒ 今天不会出现第二个 generation 的成因只有人或 Core 显式再发起）。
- 反例 a（须红）：在一份 `/tmp` 内存副本的 client 流里再追加一行 dial（generation 2），而 run 文档没有任何终态字段 ⇒ 判红。**判别式**：真 run 只有 1 行 dial ⇒ 不红。这条对照不可省：一个只数「≥1 次」的写法会恒真。
- 反例 b（须红）：账本只有一条 `FAILED` 但 reason 为空 ⇒ 判红为「缺具名分类」而不是「无重试」。
- 上限该是谁：`connection.py:164-165` 的守卫（未 close 不许 begin）是**码级**保证，不是运行期读数；把它当读数就是拿实现细节冒充证据。因此 §3.2 的判据只写「run 内计数 ≤ 具名 N」，N 由登记卡与契约商定（主控，§4 决定四）。
