## 2. 完整项目要交付什么

Minekin 是一个**能像玩家一样生活的独立 Minecraft 角色系统**，不是聊天 Bot，也不是永远执行人类指令的采集脚本。

- 运行：不依赖用户已有启动器，能准备受支持版本、进入允许的服务器，稳定启停和恢复。
- 操作：通过真实客户端观察和合法输入，导航、采集、合成、吃饭、建造、战斗与跨维度活动。
- 自主：有自己的需求、人格、目标与取舍；无人下令也能继续生活，受阻会调整或放弃。
- 连续：身份、关系、承诺、知识与经历跨会话保留；重启不换人，跨服务器不串世界事实。
- 社交：能聊天、合作、拒绝、产生误判并接受反证；人格影响实际选择而非只影响台词。
- 管理：可用且清晰的 Web 后台，能设置角色和服务器、观察运行与心智、管理生命周期和成本。
- 工程：安全的权限边界、可部署发行包、版本矩阵、故障恢复、性能和真实验收证据。
- 扩展：完整原版游戏进度、多 Kin 协作和模组适配也列入路线，不偷偷丢掉；但不阻塞首个可用单 Kin 版本。

产品主线为 **Minecraft Java 1.20.1**。1.21.4 保留为已存在的回归对象，不重新变成优先主线。自动检测版本后，选择**受支持且受审的**客户端/Bridge 配方；不支持、探测歧义或认证不符时明确拒绝/要求选择，不自动猜版本硬进。

产品语义以[原始路线](roadmap.md)、[架构](architecture.md)、[玩家旅程](player-journey.md)、[独立 Runtime 与后台](standalone-runtime-dashboard.md)及专项契约为依据。本文补足“完整步骤与阶段进度”，不废除感知、安全、身份、证据等约束。具体任务领取仍只在[执行计划](development-execution-plan.md)维护一个主干 `current_next`；本文的待开发项不是额外的 NEXT。

### S3-E：Jev 的位置与准入条件

用户提出评估 TypeSafe AI 的 [Jev 决策模型](https://docs.typesafe.ai/introduction/quickstart)。它接收状态和明确的问题/候选项，返回类型化答案与概率，适合尝试**频繁、范围已限定的局部选择**，而不是替代完整 PlayerMind。此项目前为`待开发/待实测`，不因列入规划就声称已接入。

- 本地层先用玩家等价观察、能力/权限和实时危险算出可行技能；Jev 只能在候选项内选择或给出评估，不能自行添加技能、目标坐标、隐藏事实或签发按键。选择的实际结果仍由游戏反馈核对。
- 常规 LLM 继续负责开放式目标、研究、对话、人格和长期取舍；紧急反射、动作准入、输入租约、感知边界和结果验证仍由确定性代码负责。Jev 的概率不是安全许可，也不是正确率保证。
- 完成 S3-D 后，以同一组已记录的**非隐藏**游戏状态和可行技能候选，对比 Jev、现有 LLM 与本地规则：真实任务结果、危险误判/停手、超时、平均与尾部延迟、每次有效决定费用。包含资源不足、目标失效、模型不可用等反例；不能只展示一次成功截图。
- Jev 使用独立决策适配器和可选配置，不假设它兼容现有 OpenAI chat/completions 接口；密钥仅在服务端，模型版本固定，记录决定来源/版本/成本。用户未配置时保持现有 LLM/本地路径，不偷偷发送状态到外部服务。
- 只有当对照实验说明收益与失败边界，且不降低真实任务成功率或安全性时，才考虑默认路由策略；低置信度、端点故障和分歧须保守回退或暂停，而不是扩大候选动作。实验结论可决定不接入，不能为了满足路线图而强行启用。

## 5. 后台重做的产品要求

后台不是证据阅读器的换皮。先让用户回答四件事：**它是谁、在哪个世界、正在干什么、为什么没运行/没完成**。

- 一级页面：总览、角色设置、服务器与会话、观战、心智与记忆、时间线/诊断、模型与成本。未实现页不展示假数据，不拿空白占位页充功能。
- 总览优先显示连接/运行阶段、当前目标与最后实际结果，旁边才是资源指标；操作结果要显示正在执行、已完成或具名拒绝，不出现点了没反馈。
- 身份页显示固定名称 `minekin` 的默认规则和真实存量身份。改名解释离线 UUID/服务端角色数据后果；停机、显式确认、校验和原子保存，不静默迁移。
- 服务器页明确“配置版本”“探测版本”“实际启动版本”，区分安装、连接、加入、可操作；缓存存在不代表启动成功。
- 统一排版、留白、颜色和组件状态；桌面主布局清楚，窄屏不溢出，键盘操作和错误提示可用。视觉验收提供真实页面截图与前后对比，不以测试全绿证明好看。
- Live 是实际游戏画面；Mind 是实际运行心智状态。模型/媒体尚未启用时显示真实原因；媒体不能默认成为 PlayerMind 的隐藏观察来源。
- 先完成只读视觉与已授权身份设置，再单独冻结通用管理写面；认证、防跨源、请求幂等和并发控制齐备后开放。界面不能直接向 Bridge 发任意输入、shell 或 SQL。

具体配色与布局可在实现时迭代，不提前固定几百条 CSS；但信息结构和真实功能不能缩水。

`.tmp/` 可以放一次性实验，不能成为运行项目必须依赖的入口。复用的产品逻辑进入正式模块，复用的验证进入受跟踪测试/工具；不为了提交而把临时脚本全部搬成永久设施。连续两轮只有 docs/.tmp 变化而没有对应能力交付时，主控要检查是否仍被真实缺陷阻挡；不能自动再开一轮盘点填空。

## 7. 授权、验收和完成口径

**规划覆盖不等于高影响动作已经获准。** 普通实现方法、组件划分、局部重构和界面样式由执行者判断；下面事项保留明确边界：

- 当前允许的本地受控测试继续；用户远程服 V08 仍按最新授权门处理，未重新授权不得连接或修改测试服。
- HOST/PERSIST 的宿主 generation、WorldCapsule 权威来源/落盘、缺 profile 时的一致性判断先冻结；未冻结不自行猜产品语义。
- 在线认证、扩大公网服务、存量数据删除/保留、残留进程接管分别确认；不得为绕过阻塞静默改认证或清理用户现场。
- 跨 bundle 证据载体与 required-case/mandatory 策略需要明确迁移影响、反例和独立审查；有效 PASS 不自动让全部门变绿。
- 通用 Dashboard 写控制权限需要单独冻结；已明确授权的本地身份改名不要再重复等产品决定。

遇一处待决策，只阻断依赖它的任务；继续已明确范围的独立工作。如果所有可执行项真的耗尽，一次列清决策与影响，不新增无意义审计卡。需新授权的事项仍询问用户，不以“推进完整项目”为借口越界。

每个阶段的最低验收：代码与用户入口存在；一次代表性真实使用；相关单测/集成与故障反例；可核对的版本和结果；简明启动说明。本地/Docker 优先，CI 不当完成凭据，不消耗 CI 额度反复轮询。

自主性必须区分模型自行选目标与 harness 安排的固定动作。动作完成按真实库存、世界反馈等核对，模型自述不算。普通模式不读取墙后实体、私人箱子或全图真值；可选额外感知必须显式授权并标来源。重启恢复的是人物与意图，不是旧 lease、GUI 句柄和实体 token。

**三个不同终点：**

1. 可用 demo：S0–S3 的代表性路径成立，后台可用，真实自主完成一个小目标；不能宣称完整生存人物。
2. 完整单 Kin 核心版：S0–S8 核心验收成立，能连续生活、保留人格记忆、社交与恢复，并提供可信发行方式。可选在线认证/平台若未纳入发行范围，明确列排除项，不伪称支持。
3. 整条项目路线：还包含 S9 游戏进度、S10 多 Kin 和经范围确认的 S11 模组扩展。未交付时保持待开发/延期，不能因核心版发布把它们一并写 DONE。

没有可靠权重前不报“整体完成 90%”。对用户报告已通过哪些阶段、目前在做什么、离下一可用版本还缺哪些能力。

### 8.1 完成度逐项审计（2026-10-01 按代码与真跑读数复核）

1. **后台控制逐动词核对（#4，判 PARTIAL）**：`gateway/session_control.py` 的 `_AVAILABLE_CONTROLS` 当前只有 `stop`；`start`/`pause`/`resume` 作为具名缺口写进读模型的 `unavailableControls`——start 需由持有 Bridge IPC 的活动进程发起、只读网关不托管，pause/resume 依赖冻结状态机里尚不存在的 `PAUSED` 态。连接与目标读取是 GET 只读投影，目标提交经 `config_write` 落盘而非独立生命周期写面。因此后台的授权写面是配置保存（含目标）、会话停止、身份确认式改名三处，生命周期四动词只有“停止”这一动词是真的；仅有配置与停止不能判 #4 完整通过。
2. **动态配方来源仍是待开发（#6）**：`domain/recipe_catalog.py` 的小 curated 集合能推出 product id 与数量，面板把“当前配方库覆盖不到的目标”显示成边界——这只是诚实展示，不等于配方知识来自世界。由世界/游戏真实反馈派生、能对真实目标端到端应答的动态配方来源（[GUI 合成](recipe-knowledge-gui-contract.md)、[研究技能](research-skill-contract.md) 所载）仍未开发，不能因为边界可见就跳过（见 task #47）。
3. **正常停止 ≠ 异常断连，重启读回 ≠ 任务恢复（#3）**：三者按不同路径分别验——正常取消走 `stop_session` 的“请求—活体松键—按 `/proc` 证明身份后才终止”；异常断连看 Bridge IPC 丢失与 `BRIDGE_LOST`/退出码收尾；应用重启读回的是 operator 配置（模型/目标/预算/身份），恢复的是人物与意图而非旧 lease、GUI 句柄或实体 token。三条不能互相冒充，逐条活体验证仍在进行（见 task #46）：四路区分里「正常取消/stop」与「应用重启/复用＝核对既有会话、既非静默重连（`recovery.status reconciled`）亦非重放目标（`autonomous null`）」已在活体分别取到读数（六之二十二 run `8c6197a3…`，松键按实读入账 `release released=[295]/unconfirmed []`）；「异常断连」也有一枚活体分类读数（第五节第 6 条 run：`stop_reason CONTROL_CHANNEL_LOST`、`outcome BRIDGE_LOST`、`input_release_failed true`、`unconfirmed [290]`，与正常 stop 的 `unconfirmed []` 成对照），唯由 harness 拆通道触发、非游戏内自发掉线，触发保真度列为保留项；「非空失效的显式恢复」只有设计面（重启断言刻意不要求 `invalidated` 为空）与 `invalidated []` 读数，真正非空的活体读数仍缺——四路未全绿，不得转述为已全验。
4. **确认松键必须有 released/unconfirmed 实际读数（#4 补）**：一次“已确认松键”的判定读的是 run document 的 `release.released` 与 `release.unconfirmed`，不是 `asked`/`terminated`/`unresolved`。木棍活体 run `da6b72d7…` 收尾读数为 `asked=[310]、released=[310]、unconfirmed=[]`，即每一路被按住的输入都在客户端下一 tick 得到释放确认；只有 `asked` 而无 `released`、或带非空 `unconfirmed`，一律不算确认。
