## 3. 逐格的 oracle / 载体 / 反例设计

### 3.1 `ADMIT-010`（LAN 地址 | 不扫描局域网；只连已保存 profile）

**① 「LAN 地址」这一格：今天双重不可达（推断自 #4 三处字节）。**
v1 在加载期就具名拒（`server_profile.py:190-195`）；v2 允许非 loopback 字面量存进 profile（`_literal_host:283-297` 只要求 IP 字面量），但**会话路径**仍把 managed target 关回 loopback（`:424-428` 消息原文 `remote joining needs its own authorization card`）；即使有人绕过 Core 直接发命令，Java 门禁 `AdmissionCommandGate.java:23` 也只认两个字面量。所以契约 `:130` 那一格的内网地址今天无法被本构建加入，也就无法被封证。
- 判法只能落在「拒」的那一侧：一条 case 断「保存一个 LAN 字面量 target 之后，`session start` 在启动客户端**之前**给出 `:426-428` 那条具名拒止」。载体：CLI 退出码 + `:retryability` 为 `OPERATOR_ACTION`（`server_profile.py:70-77`）。
- 反例：把 `:424-428` 的拒改成 warn 或删掉 ⇒ 该断言必须红（阳性对照：同一 fixture 下 loopback target 必须走到启动）。
- 建议具名缺口：`LAN_TARGET_SCENARIO_NOT_REACHABLE_IN_P0`（写法沿用 `assert_case_evidence.py:4054-4056` 的具名缺口先例）。
- **词义要点名**：本仓库既有 LAN 用例（`core-030.json`、`host-030.json`，即 #9 两处使用者）里的 "LAN" 是**在 127.0.0.1 上开放局域网世界**，不是契约 `:130` 的内网地址格。两者共用一个词，排卡时必须分开写，否则 010 会被 030/HOST-030 的读数冒充。

**② 「不扫描局域网」：两半，一半今天可判、一半无载体。**
- （甲）**码级负空间**：#12 的读数是本轮亲量的——`src/**` 里 `scan` 只出现在「拒止」语境，`bridge/**` 对 vanilla 局域网列举类（`ServerListLanGame*`）与 `_minecraft._tcp` 均 0 命中（命令 F）。形状与 `ADMIT-030` ④ 的「Bridge 零重试码」同族：**码级事实**，可作判据的一条腿。
- （乙）**运行期**：无载体。账本连接行只有 `phase`/`reason`（#7），客户端日志只在被要求拨号时打一行（#3）；「没有扫」在封存材料里没有对应字节。
- 恒真风险与对策：判「不存在」的断言必须自带**阳性对照**——在同一次 run 材料里能读到「被要求的目标恰好是 profile 那一个」（见 ③），并把「目标集合 ⊆ {profile endpoint}」写成对 `_DIALLED` 全部命中行的计数判法，而不是「搜不到扫描字样就算绿」。搜字面量本身不作判据（同 `ADMIT-030` ③ 的教训：词缺不等于场景可达）。

**③ 「只连已保存 profile」：形状今天可达且载体齐备，是可排真跑的那一格。**
三条等式，各自独立可判：
1. **拨号等式**（新格，本轮证其缺失）：`_DIALLED` 的 `host`、`port` 两个分组分别等于 sealed profile（#8）的 `host`、`port`。既有两条使用者都没做这件事：`:1353-1358` 比的是宿主 run 公布的端口，`:1401-1402` 只断「是不是 loopback 字面量」。反例 a：把 profile 端口改成 `25565` 而日志行拨 `25566` ⇒ 红。反例 b：profile 材料缺失 ⇒ 必须落 `NO_SEALED_SERVER_PROFILE`（#8 先例 `:2610-2611`）而不是绿。
2. **代次等式**：`_DIALLED` 第三个分组（generation）与本 run 的 `AuthPolicyFrozen`/`SessionProcessStarted` 的 generation 一致（载体 `session_log.py:113-159`、`admission.py:143-146`）。
3. **revision 等式**：Core 只接受 id/revision 与在途 attempt 相等的生命周期报告（`admission.py:143-146`），Java 门禁另要求 revision 是 64 位十六进制（`AdmissionCommandGate.java:22`）——这一条已有域测，本卡不重判，只登记它是 010 的第三腿。
- 判别式（写死在卡面上）：**不得拼字符串比**。Core 侧 `endpoint()` 给 IPv6 加方括号（`server_profile.py:100`、`:251`），而日志里是 vanilla `ServerAddress.toString()` 的形式——两者是否逐字相同**本卡未测**（未核 vanilla 字节，见 §6 未测清单）。按分组分别比可避开这个坑。

### 3.2 `ADMIT-020`（SRV 目标 | 保存原始地址与实际 endpoint；重定向仍过策略）

**① 「保存原始地址」：wire 上有、产品事件里没有、封存材料里有。**
`ConnectWorld.original_host`（#1 `:23`）就是契约 `:70` 的「原始目标」；但它不进账本行（#7 `session.py:1531-1536` 只写 `phase`/`reason`）。今天能被复审者读到的「原始地址」只有 #8 那份封存 profile 文档。⇒ 可判等式与 3.1 ③ 的第 1 条重合，本卡不重复计一格绿；**独立可判的只有**：profile 文档进 bundle（`seal_run_evidence.py:235-239` 的 `SERVER_PROFILE_ARTIFACT` 落盘分支）且 `revision` 与 profile 字节自洽（`server_profile.py:219`、`:394` 的 `sha256(canonical)`）。

**② 「实际 endpoint」：加入路径今天无载体（本轮最强结论）。**
#3 的日志行打在 `ConnectScreen.connect`（`ClientAdmissionController.java:630`）**之前**，内容是 `address`（`:606` 由命令的 `original_host:port` 构造）。vanilla 的 DNS/SRV 解析发生在那之后，Bridge 从不读回——它读回的唯一东西是资源包策略（`:610-613`，注释自陈「read back rather than echoed」）。⇒ 即使真发生重定向，封存材料里「被要求的地址」与「实际 socket 端点」在字节上不可区分。建议具名缺口：`RESOLVED_ENDPOINT_HAS_NO_CARRIER_ON_JOIN_PATH`。
- **不得拿探针的 `resolution_chain` 顶这一格**（#6）：那是另一条路径（`server_probe.py:10-11` 自陈不建 session），而且生产解析器零查询（`:71-75`），链里第二段永远等于第一段。
- 唯一能补的载体是扩 `ConnectionLifecycle`（#1/#2 所属 proto）或加一条 Bridge 日志行读回真实端点；两者都**移动 Bridge jar 摘要**（`seal_run_evidence.py:135-138` 的 jar 哈希），按 `project-reseal-is-atomic` 口径属重封全卷 ⇒ 交主控（§4 第 3 条）。

**③ 「重定向仍过策略」：三条路，只有第一条今天真的判得动，且它判的不是加入。**
- （甲）**域级可判**：`server_probe.py:290-299` 在 transport 之前重决策，`tests/unit/test_server_probe.py:89-104` 已经用注入 resolver 把 `10.0.0.5`（LAN 字面量）在 `as-saved` 与 `via_srv` 两种形状下都判成 `POLICY_REFUSAL` 且 `transport.calls == []`。这是真材料，但它是「探针域内的重决策有测」，**不是**「一次真实 SRV 重定向被拦住」——`FakeResolver` 是测试自己造的对象（`:42-46`）。同一形状的教训已在 `ADMIT-070` 落地过（契约 `:136`：五条断言全登记为 pytest，测的是域内过滤器）。
- （乙）**Java 门禁只检被要求的地址**：`AdmissionCommandGate.java:23` 检的是 `original_host`，检不到解析结果。自测 `AdmissionCommandGateSelfTest.java:19` 那条 `example.com` 反例证的是同一个 `isLoopback` 谓词，**不证**「解析后仍在策略内」；而且「LAN 字面量被门禁拒」与「端口越界被门禁拒」两条反例目前都没有（#11）。
- （丙）**真 SRV 场景不可达**：profile 的 host 必须是已规范化的 IP 字面量（`server_profile.py:283-297`；v1 走 `decide_endpoint` 的 `NOT_A_LITERAL`，`admission.py:134-137`），域名在加载期即拒。⇒ 缺口候选 `SRV_SCENARIO_NOT_REACHABLE_BY_PROFILE`（与 `ADMIT-030` ③ 的 `DNS_SCENARIO_NOT_REACHABLE_BY_PROFILE` 同一族、同一根因：profile 层禁止携带可解析名字）。
